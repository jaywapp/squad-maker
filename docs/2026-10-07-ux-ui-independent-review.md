# squad-maker UX/UI 독립 검토 (2026-10-07)

- 대상 서비스: https://jaywapp.github.io/squad-maker/ (화면 표기 `beta 1 (2026-07-21)`)
- 대상 저장소: github.com/jaywapp/squad-maker, `main` 94e7705 기준 (fc-squad-maker와 무관)
- 범위: 분석과 개선 제안만 했다. 코드와 기존 문서는 고치지 않았다.
- 독립성: 기존 검토 문서(`2026-07-18-ui-ux-review.md`, `ad-placement.md` 등)는 읽지 않고 작성했다. 결론이 겹치거나 충돌하는지는 따로 대조해야 한다.

## 0. 검토 환경과 근거 표기

| 구분 | 내용 |
|---|---|
| 브라우저 | Playwright MCP가 띄운 Chromium 계열 브라우저. 사용자 Chrome과 분리된 격리 프로필을 썼다 |
| 데스크톱 | 뷰포트 1440×900, 마우스 입력 |
| 모바일 | 뷰포트 360×800, DPR 3, `isMobile`·`hasTouch` 켬, Android Chrome UA. **Chromium 에뮬레이션이며 실제 Android 기기 검증이 아니다** |
| 터치 입력 | CDP `Input.dispatchTouchEvent`와 Playwright `touchscreen.tap`으로 드래그·탭·길게 누르기를 흉내 냈다 |
| 데이터 | 격리 프로필의 임시 데이터만 썼다(팀명 `UX테스트FC` 등). 끝난 뒤 localStorage를 비우고 브라우저를 닫았다 |
| 외부 전송 | 제보 전송, 클립보드 복사 후 외부 앱 붙여넣기, 카카오톡 공유는 하지 않았다. 페이지 네트워크 요청은 문서·폰트·html2canvas·gif.js 로드뿐이었고 분석·광고 요청은 관찰되지 않았다 |

근거는 아래 세 가지로 표기했다.

- **[관찰]** 위 환경에서 직접 조작해 확인했다.
- **[소스]** `index.html`을 읽어 확인했다. 화면에서는 재현하지 않았다.
- **[추정]** 검증하지 않은 추론이다. 실제 기기나 추가 테스트로 확인해야 한다.

1. 처음 진입했을 때 데스크톱과 모바일 첫 화면, 전체 페이지 [관찰]
2. 팀명 입력, 선수 선택, 드래그 이동, 더블클릭 이름 수정, 우클릭과 길게 누르기 메뉴 [관찰]
3. 포메이션 초기화, 인원(5vs5~11vs11) 변경 [관찰]
4. 전술 패턴: 경로 그리기, 단계 추가, 미리보기 영역 [관찰]
5. 새로고침 후 자동 저장 복원, `.sq` 파일 저장·불러오기, 잘못된 파일 불러오기 [관찰]
6. PNG 이미지 저장, GIF 저장(2단계, 다운로드 파일 프레임 확인), 단톡방 공유 모달, 공유 링크를 새 탭에서 열어 본 열람 모드 [관찰]

결과에서 제외한 항목: 처음에 Playwright `fill`로 팀명을 넣고 새로고침했을 때 팀명이 사라졌지만, 실제 키 입력으로 다시 해 보니 정상 저장됐다. 자동화 도구 때문에 생긴 현상으로 보고 결함에서 뺐다. 모바일에서 버튼 탭이 다른 요소에 가로막힌 것처럼 보인 현상도 `elementFromPoint`로 확인해 보니 겹침이 없었다. 도구의 스크롤 처리 때문으로 보고 제외했다.

## 1. 전체 평가

축구장을 화면의 주인공으로 둔 다크 그린 톤 전술 보드다. 피치 렌더링, 번호가 매겨진 원형 선수 토큰, Oswald 워드마크가 조기축구 사용자에게 바로 축구 도구로 읽힌다. 모바일 360px에서 가로 넘침이 없었고 피치가 첫 화면을 차지했다. 터치 드래그 중에 페이지가 스크롤되지 않았다는 점도 좋다.

반면 **편집 데이터 보호가 약하다.** 인원 변경 한 번으로 선수 이름, 세 스쿼드의 배치, 전술 패턴이 확인도 되돌리기도 없이 사라진다. 파일 불러오기도 현재 작업을 묻지 않고 덮어쓴다. 앞으로 저장 슬롯으로 수익화하려면 "내 전술이 안전하다"는 신뢰가 먼저 있어야 하므로 이 부분을 가장 먼저 고쳐야 한다.

그다음 문제는 **정보 위계**다. 저장·내보내기·공유 버튼이 세 군데에 흩어져 있다. 라임 그린 강조색을 6곳 이상에서 써서 주 행동이 하나로 보이지 않는다. 데스크톱에서는 선택한 선수의 작업 도구가 첫 화면 밖에 나타난다.

## 2. 유지할 강점

1. **피치 중심 구성과 정체성** [관찰]: 짙은 녹색 줄무늬 피치, 흰 라인, 번호 원형 토큰, GK 빨강이 한눈에 축구 전술판으로 읽힌다. 다크 배경(#141A16)과 피치 녹색이 같은 계열이라 화면 전체가 하나의 세계로 보인다.
2. **모바일 기본기** [관찰]: 360px에서 가로 스크롤이 없다(`scrollWidth` 360). 피치가 첫 화면에 다 들어온다. 터치 드래그 중 스크롤 충돌이 없었다(scrollY 변화 0). 길게 누르면 뜨는 메뉴의 색상 견본과 항목이 크다.
3. **되돌리기·확인 패턴의 씨앗** [관찰/소스]: 선수·패턴·단계·경로 삭제에는 5초 "되돌리기" 토스트가 있다. 기본 `confirm` 대신 포커스 트랩·Esc·포커스 복귀를 갖춘 자체 대화상자(`uiConfirm`)를 쓴다.
4. **공유받은 사람의 데이터 보호** [관찰/소스]: 공유 링크는 읽기 전용 열람 모드로 열린다. 이 모드에서는 자동 저장이 꺼진다. "내 스쿼드로 가져오기"는 덮어쓰기 확인을 받는다.
5. **GIF 내보내기 품질** [관찰]: 2단계 패턴 기준으로 약 2.6초 걸렸다. 480×660, 78프레임, 약 2.1MB이고 단계 라벨이 들어간다. 진행률을 퍼센트로 보여 준다.
6. **접근성 기초** [관찰]: `lang="ko"`, 선수 토큰 `role="button"`과 의미 있는 `aria-label`, 토스트 `aria-live="polite"`, 탭 `role="tab"`과 `aria-selected`가 있다.

## 3. 개선점

형식: **화면·재현 / 관찰 근거 / 사용자 영향 / 변경안 / 검증 방법**

### P0 — 핵심 데이터 손실

#### P0-1. 인원 버튼 한 번으로 선수·배치·전술 패턴이 확인 없이 초기화된다

- **화면·재현**: 스쿼드 탭 → 오른쪽(모바일은 피치 아래) "인원" 줄. 선수 이름을 바꾸고 다른 스쿼드 배치나 전술 패턴 경로를 만든다. 팀·선수 지침은 비워 둔다. 그 상태에서 다른 인원 버튼(예: 8vs8)을 누른다.
- **관찰 근거** [관찰]
  - GK 이름을 `김골키`로 바꾼 뒤 8vs8을 누르자 확인창 없이 이름이 `GK`로 돌아갔다. 자동 저장된 localStorage 값도 `GK`로 덮어써졌다.
  - 2단계 경로가 있는 전술 패턴이 9vs9 전환 뒤 빈 단계 1개로 초기화됐다. 저장 데이터도 `s:[{m:{}}]`가 됐다.
  - Ctrl+Z, 토스트 되돌리기 모두 없었다.
  - 지침이 한 줄이라도 있으면 "모든 스쿼드와 지침이 초기화됩니다" 확인창이 뜬다.
- **원인** [소스]: `onModeChange()`(`index.html:1430`)가 지침(`teamNote`, `playerNotes`)이 있을 때만 확인한다. `initAllSquads()`는 로스터·세 스쿼드·패턴을 모두 다시 만든다.
- **사용자 영향**: 인원 버튼 7개가 팀명 입력 바로 아래 촘촘하게 붙어 있어서 잘못 누르기 쉽다. 선수 이름을 바꾸고 배치만 해 둔 사용자(지침을 안 쓰는 대다수로 추정)는 한 번 잘못 눌러 작업 전체를 잃는다. 기기 안에만 저장되므로 복구할 길이 없다.
- **변경안**(작은 순서대로)
  1. 확인 조건을 "지침 존재"에서 "기본값과 다른 사용자 변경 존재"로 넓힌다. 이름 변경, 위치 이동, 패턴 경로, 팀명을 포함한다. 확인 문구에 사라지는 대상을 구체적으로 적는다. 예: "선수 이름 9명, 스쿼드 3개 배치, 전술 패턴 1개가 초기화됩니다."
  2. 변경 직전에 `captureUndo()`를 호출하고 기존 `showUndoToast()`로 "8vs8로 바꿨습니다 · 되돌리기"를 띄운다. 기존 장치를 재사용하므로 비용이 작다.
  3. (후속) 인원을 바꿀 때 기존 선수 이름·색을 순서대로 유지하고 늘거나 준 인원만 조정한다. 초기화 자체를 줄이는 방향이다.
- **검증 방법**: 이름만 바꾼 상태, 패턴만 있는 상태, 지침만 있는 상태 각각에서 인원을 바꿔 확인창 노출과 되돌리기 복원을 본다. 새로고침 뒤에도 복원 상태가 유지되는지 확인한다. 아무것도 바꾸지 않은 첫 화면에서는 확인 없이 바로 바뀌는지도 확인한다(불필요한 확인 방지).

### P1 — 큰 혼란·신뢰 저하

#### P1-1. 파일 불러오기가 묻지 않고 덮어쓰고, 불러온 내용은 저장되지 않는다

- **화면·재현**: 스쿼드 탭 하단 "파일 불러오기" → `.sq` 선택.
- **관찰 근거** [관찰]: 팀명이 `덮어쓰기전팀`인 상태에서 다른 `.sq`를 불러오자 확인창도 성공 토스트도 없이 화면이 바뀌었다. 그런데 localStorage에는 여전히 `덮어쓰기전팀`이 남았다. 새로고침하자 불러오기 전 상태로 돌아갔다. 잘못된 파일에는 "올바른 .sq 파일이 아닙니다." 토스트가 정상적으로 떴다.
- **원인** [소스]: `loadSquadFile()` → `applyState()`(`index.html:3471`, `3540`)가 `autoSave()`를 호출하지 않는다. 확인과 되돌리기도 없다.
- **사용자 영향**: 덮어써서 지금 작업을 잃을 수 있다. 반대로 백업을 복원했다고 믿었는데 다음 진입 때 옛 상태로 돌아가 "복원이 안 된다"고 느낀다. 백업·복원 기능 자체의 신뢰가 떨어진다.
- **변경안**: 불러오기 전에 "현재 작업을 `<파일 팀명>`으로 바꿀까요?"를 확인한다. 적용 직전에 `captureUndo()`, 적용 뒤에 즉시 저장하고 "`<팀명>` 백업을 불러왔습니다 · 되돌리기" 토스트를 띄운다.
- **검증 방법**: 불러오기 → 새로고침 → 불러온 팀명이 유지되는지 확인한다. 취소하면 현재 상태가 그대로인지, 되돌리기로 이전 상태가 복원되는지 확인한다.

#### P1-2. 모바일에서 선수를 탭해도 선택되지 않아 하단 작업 툴바를 쓸 수 없다

- **화면·재현**: 모바일 360×800 → 스쿼드 탭 → 선수 토큰을 짧게 탭한다.
- **관찰 근거** [관찰, Chromium 터치 에뮬레이션]: 탭 뒤 `.player.selected`가 없었고 `#playerActions`는 보이지 않았다(버튼 크기 0×0). 길게 누르기(0.8초)로는 색상·이름·삭제 메뉴가 정상으로 열렸다.
- **원인** [소스]: 필드의 `touchstart`가 `e.preventDefault()`를 호출한다(`index.html:2015`). 그래서 브라우저가 터치 뒤 `click`을 만들지 않는다. 선택은 `click` 핸들러에만 걸려 있다(`index.html:1856`). 모바일용으로 하단 고정한 툴바(`index.html:649`)에 탭으로는 닿을 수 없다. 더블탭 이름 수정도 같은 이유로 안 될 가능성이 높다[추정].
- **사용자 영향**: 모바일 사용자에게는 길게 누르기만 남는다. 길게 누르기는 발견성이 낮고, 드래그 시작과 헷갈려 실수로 선수를 옮기기 쉽다. 데스크톱의 "선택 → 작업" 모델과 모바일 모델이 서로 달라진다.
- **변경안**: `touchend`에서 이동 거리 8px 미만이고 길게 누르기 타이머가 끝나기 전이면 `selectPlayerForEdit(id)`를 호출한다. 이미 계산 중인 이동 거리 값을 그대로 쓰면 된다.
- **검증 방법**: **실제 Android 기기(Chrome, 가능하면 Samsung Internet 포함)** 에서 탭 → 툴바 표시, 드래그 → 선택 없이 이동, 길게 누르기 → 메뉴를 각각 확인한다. 에뮬레이션 결과만으로 확정하지 않는다.

#### P1-3. 데스크톱 1440×900에서 선택 툴바·조작 힌트·GK가 첫 화면 밖에 있다

- **화면·재현**: 1440×900 → 스쿼드 탭 → 선수 클릭.
- **관찰 근거** [관찰]: 피치 높이 때문에 GK 토큰이 화면 아래로 잘린다. 조작 힌트(`드래그: 위치 이동 | 더블클릭 …`)는 y≈980이다. 선수를 클릭하면 뜨는 작업 툴바는 y=1000~1085로, 900px 뷰포트 밖에서 열려 클릭해도 아무 반응이 없는 것처럼 보인다. 좌우에는 각각 230px 정도의 빈 공간이 있다.
- **사용자 영향**: "선택하면 무엇을 할 수 있는지"가 보이지 않는다. 노트북 화면(768~900px 높이)에서 주 편집 대상인 피치 전체를 한 번에 볼 수 없다.
- **변경안**: 데스크톱에서 피치 높이를 `min(뷰포트 높이 - 상단 영역, 기존 최대치)`로 맞춘다(기존 `applyFieldScale` 활용). 선택 툴바는 오른쪽 패널 맨 위에 "선택한 선수" 카드로 두거나 모바일처럼 하단 고정한다. 조작 힌트는 피치 바로 위나 안쪽 모서리로 옮긴다.
- **검증 방법**: 1366×768, 1440×900, 1920×1080에서 GK·힌트·선택 툴바가 스크롤 없이 보이는지 확인한다.

#### P1-4. "↺ 초기화"가 확인·되돌리기 없이 현재 스쿼드 배치를 지운다

- **화면·재현**: 선수를 옮긴 뒤 포메이션 선택 옆 "↺ 초기화"를 누른다.
- **관찰 근거** [관찰]: 클릭 즉시 옮긴 선수가 기본 위치로 돌아갔다. 확인창·토스트가 없었다. [소스] `resetLayout()`(`index.html:1642`)에 `captureUndo`가 없다.
- **사용자 영향**: 공들인 배치를 한 번 클릭으로 잃는다. 버튼이 포메이션 선택 바로 옆, 모바일에서는 피치 바로 위라 잘못 누를 위험이 있다.
- **변경안**: 확인창 대신 기존 패턴과 같은 `captureUndo()`와 "배치를 초기화했습니다 · 되돌리기" 토스트를 붙인다. 확인보다 흐름을 덜 끊는다.
- **검증 방법**: 초기화 → 되돌리기 → 원래 위치 복원 → 새로고침 뒤에도 유지되는지 확인한다.

#### P1-5. 자동 저장이 보이지 않고 저장 실패는 조용히 무시된다

- **관찰 근거** [관찰]: 드래그·이름 수정은 약 0.6초 뒤 localStorage에 저장되고 새로고침 뒤에도 복원됐다. 그러나 화면에 저장 상태 표시가 없다. 도움말에만 "자동 저장되어 새로고침해도 유지됩니다"라고 적혀 있다. [소스] `autoSave()`의 `catch {}`(`index.html:3711`)가 저장 실패(저장 공간 초과, 사생활 모드 제한 등)를 사용자에게 알리지 않는다.
- **사용자 영향**: 사용자는 "파일 저장"을 눌러야 저장되는 줄 알 수 있다. 저장이 실패해도 모른 채 작업을 계속하다 데이터를 잃는다[추정]. 앞으로 "저장 슬롯" 개념을 넣으려면 지금 무엇이 어디에 저장되는지를 보여 주는 기반이 필요하다.
- **변경안**: 팀명 옆이나 상단에 작은 상태 텍스트("이 기기에 저장됨")를 둔다. 실패하면 닫을 수 없는 경고 줄을 띄운다. 예: "이 브라우저에 저장하지 못했습니다. 백업 파일을 받아 두세요 [백업 받기]".
- **검증 방법**: DevTools에서 `localStorage.setItem`을 예외로 바꾸고 편집해 경고가 뜨는지 본다. 정상 편집에서는 상태 텍스트가 깜빡임 없이 갱신되는지 확인한다.

#### P1-6. 저장·백업·내보내기·공유의 구분과 결과가 불명확하다

- **관찰 근거**
  - [관찰] 버튼이 세 군데에 흩어져 있다. "이미지 저장"은 오른쪽 패널 위, "GIF 저장/전체 패턴 GIF"는 전술 패턴 탭, "단톡방 공유 텍스트 생성/파일 저장/파일 불러오기"는 페이지 맨 아래(데스크톱 y≈1270, 첫 화면 밖)에 있다.
  - [관찰] "파일 저장"이 두 가지 뜻으로 쓰인다. 하단 버튼은 `.sq` 백업을, 공유 모달 안 버튼은 공유 텍스트 `.txt`를 받는다.
  - [관찰] PNG·GIF 저장이 성공해도 토스트가 없다. 다운로드 표시는 브라우저에 맡겨 둔다.
  - [소스] PNG 실패 시 통계 기록만 하고 메시지는 없다(`index.html:2111`). GIF는 워커·인코딩 실패 처리가 없어 진행 오버레이가 남을 수 있다(`index.html:2667~2735`)[추정, 미재현].
  - [관찰] 모바일에도 OS 공유 시트(Web Share API) 연결이 없다. 이미지는 다운로드 → 갤러리 → 카카오톡으로 사용자가 직접 옮겨야 한다.
- **사용자 영향**: 조기축구 사용자의 핵심 목표는 "단톡방에 전술 올리기"다. 그런데 이미지·GIF·링크·텍스트 중 무엇을 써야 하는지, 저장과 공유의 차이가 무엇인지 화면에서 바로 알 수 없다.
- **변경안**
  1. 하나의 "내보내기·공유" 진입점(버튼 1개 → 시트)으로 모은다. 시트는 세 그룹으로 나눈다. ① 이미지·GIF(보내기/저장), ② 링크·텍스트(단톡방용), ③ 백업(.sq 받기/복원).
  2. 이름을 정리한다. "파일 저장" → "백업 파일 받기(.sq)", "파일 불러오기" → "백업에서 복원", 공유 모달의 "파일 저장" → "텍스트 파일로 받기".
  3. 결과 피드백을 단다. 성공하면 "`UX테스트FC_기본 스쿼드_3-3-1.png` 저장됨" 토스트, 실패하면 원인과 재시도 버튼을 보여 준다. GIF 진행 오버레이에 취소 버튼을 두고 실패하면 닫히게 한다.
  4. `navigator.canShare({files})`가 가능한 환경에서는 "보내기"로 PNG·GIF를 OS 공유 시트에 바로 넘기고, 아니면 다운로드로 대체한다. Android 앱에서는 네이티브 공유로 바꾼다.
- **검증 방법**: 처음 쓰는 사용자 3~5명에게 "이 전술을 단톡방에 이미지로 올려 보세요" 과제를 주고 성공률·소요 시간·잘못 누른 버튼을 기록한다. 실제 Android 기기에서 공유 시트 → 카카오톡 전송까지 확인한다.

## 5. 광고 배치 제안 (현재 광고 없음 [관찰])

편집 화면에서는 손가락이 피치 위와 하단 고정 툴바 사이를 계속 오간다. 이 영역에 광고가 들어가면 잘못 누르기를 유도하게 된다.

**피할 곳**

- 피치 바로 아래나 위의 배너. 모바일 조작 힌트와 하단 고정 선수 툴바(`bottom:10px`)와 겹치고, 드래그가 끝나는 지점과 가깝다.
- 화면 하단 고정 배너. 선수 툴바와 엄지 영역이 겹친다.
- 내보내기 버튼을 누른 직후 다운로드 전에 뜨는 전면 광고. 결과물을 볼모로 잡는 구조라 첫 공유 경험을 해친다.
- 공유 모달의 "텍스트 복사·링크 복사" 버튼 근처.

**후보 위치**(우선순위 순)

1. **내보내기 완료 뒤 결과 카드 아래**: "저장됨/보내기 완료" 결과 안내 아래 광고 카드 1개. 사용자가 작업을 마친 시점이라 편집을 방해하지 않는다.
2. **매치 전략 탭 아래쪽**: 읽기 위주 화면이라 드래그 충돌이 없다.
3. **(향후) 전술 파일 목록 화면**: '팀=프로젝트, 전술=파일' 구조가 생기면 목록 사이 고정 칸 1개. 슬롯 결제 안내와 시각적으로 분리한다.

**공통 규칙**: "광고" 라벨을 붙인다. 인접한 조작 요소와 최소 24dp 간격을 둔다. 버튼과 같은 색·모양을 쓰지 않는다. 편집 중(선수 선택·드래그·단계 편집) 화면에는 넣지 않는다.

**검증**: 광고 자리를 빈 상자로 먼저 넣은 시제품으로 오탭률(광고 클릭 직후 1초 안에 뒤로 가기)과 편집 완료율 변화를 비교한다.

## 6. 현재 정체성을 살리는 시각적 개선 방향 2개

### 방향 A — "나이트 피치" 정돈 (추천)

- 지금의 다크 그린과 피치 녹색, Oswald 워드마크를 그대로 유지한다.
- 피치를 뷰포트 높이에 맞춘 단일 주인공으로 두고, 오른쪽 패널을 "선택한 선수 → 팀 설정 → 지침" 순서의 조용한 도구 레일로 정리한다.
- 라임은 주 행동(내보내기·공유) 하나에만 쓴다. 선택 상태는 테두리와 밝기로 표시한다.
- 선수 라벨에 어두운 반투명 바탕을 깔아 라인과 겹쳐도 읽히게 한다. 숫자는 Oswald 고정폭 숫자로 정돈한다.
- **추천 이유**: 이미 갖춘 정체성을 버리지 않고 P1-3, P1-6, P2-2, P2-4를 같은 작업 안에서 해결한다. 재작성 없이 CSS·배치 조정 위주라 위험이 가장 작다.

### 방향 B — "작전판" 내보내기 테마

- 앱 화면은 A를 유지한다. **내보내는 PNG·GIF에만** 작전판 느낌의 템플릿(분필·마커 질감의 화살표, 상단 팀명 헤더 띠, 하단 작은 앱 표기)을 옵션으로 제공한다.
- 단톡방에 올라간 이미지가 다른 전술판 앱과 구별된다. 이미지를 받은 사람이 앱을 알게 되는 경로도 된다.
- **장단점**: 공유물의 차별화와 바이럴 효과가 크다. 다만 템플릿 렌더링을 따로 만들어야 하고, 앱 화면과 결과물의 톤이 달라 일관성을 관리해야 한다.

**추천**: A를 기본으로 진행한다. B는 내보내기 구조(P1-6)를 정리한 뒤 템플릿 옵션 하나로 실험한다. 실제 화면 작업에 들어갈 때는 저장소 규칙에 따라 `docs/ux-concepts/<slug>/`에 콘셉트 3종을 먼저 만들고 선택을 받아야 한다.

## 7. 먼저 실행할 개선과 보류할 것

### 먼저 실행 (5개)

1. **P0-1 인원 변경 보호**: 확인 조건을 넓히고 되돌리기 토스트를 붙인다. 데이터 손실을 막는 가장 작은 변경이다.
2. **P1-1 파일 불러오기 보호와 저장**: 확인, 되돌리기, 즉시 저장, 성공 토스트.
3. **P1-4 초기화 되돌리기**: 기존 `captureUndo`/`showUndoToast`를 재사용해 한 줄 수준으로 고친다.
4. **P1-2 모바일 탭 선택**: `touchend`에서 탭을 판정한다. 실제 Android 기기 확인을 완료 조건에 넣는다.
5. **P1-5와 P1-6 일부**: 저장 상태 표시와 실패 경고, 내보내기 성공·실패 토스트, "파일 저장" 이름 정리. 진입점을 하나로 모으는 큰 정리는 다음 단계로 미룬다.

### 보류

- 화면 전체 재설계와 방향 B 내보내기 템플릿: 위 보호 장치와 내보내기 구조를 정리한 뒤 콘셉트 3종 절차로 진행한다.
- 다단계 실행 취소/다시 실행(Ctrl+Z/Y) 전체 구현: 단건 되돌리기로 충분한지 사용 데이터를 본 뒤 결정한다.
- 저장 슬롯·결제·광고 SDK UI: 무료 수량·가격·구독이 아직 미정이므로 화면 자리만 비워 두고 구현하지 않는다.
- 팀 공간·클라우드 공유: 2차 로드맵. 지금 없는 것은 결함이 아니다.
- 캔버스 키보드 편집: 텍스트 요약(P2-10 단기안)부터 하고 방향키 이동은 후순위로 둔다.
