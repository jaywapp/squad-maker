## 최초 요청과 권한

사용자: “A가 좋겠다. 기획서부터 상세하게 만들어서 깃헙에 문서화해서 올리자”, “웅 레포에서 다른 시안이나 불필요한 문서는 이참에 정리까지 해줘”.

최초 문서 작성·정리·GitHub 전용 브랜치 게시·Draft PR 생성 권한이 있었다. A 선택은 운영 구현 승인으로 확대하지 않았다. [PR #40](https://github.com/jaywapp/squad-maker/pull/40)은 이후 사용자의 별도 병합 요청으로 main에 병합됐다.

## 실행계획 보강 요청과 현재 범위

후속 사용자 요청: “작업계획서도 필요해”, “UI작업은 클로드가 잘하더라”. 기존 tasks를 단일 로드맵으로 상세화하고 UI·시각·반응형·접근성 담당을 Claude로 확정한다. 기능·저장·Android·SDK·통합 검증의 Codex 배정과 모델 계열/추론 수준은 제안이다. 실제 모델·착수일을 확정하지 않으며 현재 문서 스레드에서 외부 Claude에 연락하지 않는다.

추가 사용자 지시: “계획이 세워지면 내 pc에서 'squad-maker ' codex세션에서 작업하면 됨. Claude도 같은 이름의 세션 만들어놓음.” 후속 구현은 사용자 지정 PC 기존 Codex 세션에서, UI는 지정 Claude 세션에서 진행한다. 이름·ID·실제 저장소 경로·최근 상태를 지원되는 앱 도구로 대조한 뒤 인계하며 이름만으로 임의 세션에 전송하지 않는다. 이 스레드에서는 세션 확인과 인계 가능 경로 조사까지만 수행한다. 세션 ID·개인 PC 경로·비밀값은 공개 문서에 기록하지 않는다.

추가 승인: 지정 세션에서 자율 진행해 `gyungchung-mobile`, 사용자가 말한 `gyungchung-release`처럼 설치 가능한 APK를 GitHub Releases에 올려 사용자가 확인할 수 있게 한다. 실제 참조 저장소는 `jaywapp/gyungchung-mobile` 및 `jaywapp/gyungchung-releases`다. 빌드·검증·체크섬·게시 구조만 참고하고 다른 앱의 키·앱 ID는 재사용하지 않는다. 새 서명 자격 증명·영구 접근 설정은 필요 내용을 구체화한 뒤 사용자 승인을 요청한다. 테스트용 APK를 정식 배포용 서명/스토어 출시로 설명하지 않는다.

이번 스레드의 실행 범위는 문서 보강·전용 브랜치 커밋/게시·Draft PR와 지정 세션 확인이다. 사용자가 허용한 후속 구현 착수는 지정 기존 세션에 적용하며 이 스레드에서 대신 구현하지 않는다. 미정 제품·보안·계정 항목은 해당 구현 게이트를 유지한다. 현재 문서 PR의 main 병합·배포와 운영 index.html·테스트·인증·결제·광고 설정 변경은 범위 밖이다. PR #40의 이전 병합 권한을 새 PR에 적용하지 않는다.

- 현재 원격 main 기준: \`565366114d4b10a6bc7928c24754910cadd97e15\` (PR #40 squash). 최초 기준 \`e5877ddf198aaf54082d535a8c1894c346984973\` 이후 변경은 이미 병합된 문서 정리다.
- 기존 로컬 상태 조회는 다시 sandbox 초기화 오류로 차단. 기존 파일·브랜치·설정을 보존하고 GitHub 커넥터로 문서 작업을 한다. 원격 공개 문서는 읽었지만 로컬에만 있는 .agents/skills와 미커밋 변경은 확인하지 못했다.
- 같은 index.html 동시 편집을 막기 위해 계약·파일 경계를 먼저 정하고 Codex/Claude를 별도 실행 트리로 인계한다. 현 문서는 혼합 실행 세션이 아닌 조정 진입점이며 실제 실행 문서는 후속 착수 시 작성한다.
- 제품 결정은 기존 Q1~Q11를 유지한다. Q8은 최종 공유 배치에, Q3/Q4는 구매 도입에, Q10은 2차에 적용하고 해당하지 않는 첫 출시 전체를 차단하지 않는다. 광고 실제 SDK 연동은 Android 저장·복원·공유·오프라인 증거 이후다.
- 완료 기준: 기존 문서 6개만 보강, 20개 후속 작업별 목적/역할/추천 model·effort/의존성/병렬/입출력/예상 파일/verification/status, UI 계약·인계, 정적 링크·비문서 무변경·원격 Draft 검증. 앱 구현 완료를 주장하지 않는다.

## 최초 기획·정리 시작 상태와 지침

- 원격 main: `e5877ddf198aaf54082d535a8c1894c346984973`. 작업 시작 시 요청 기준점 이후 변경 없음.
- 전체 Git 트리 recursive 응답 `truncated=false`로 문서와 자산을 전수 확인.
- AGENTS.md, CLAUDE.md, README와 기존 분석·설계·작업 및 독립 검토를 읽음. Codex로 별도 문서 작업 트리를 기록. AGENTS의 병렬 검토 규칙에 따라 독립 근거 검토는 Codex 하위 에이전트에 맡기고 부모가 핵심 내용을 재확인.
- 로컬 exec는 `helper_sandbox_lock_failed` / Windows 접근 오류로 시작하지 못함. 로컬 브랜치·git status·미커밋 변경은 미확인. 로컬 파일·설정·브랜치를 수정하지 않고 GitHub 커넥터만 사용.
- 원격 트리에 `.agents/skills/` 및 추가 AGENTS/CLAUDE는 없음. 로컬에만 존재하는 지침은 실행 차단으로 확인 불가. 제공된 executor skill 목록에서도 impeccable/design-taste-frontend는 발견되지 않음.
- 이번 작업은 이미 선택된 시안의 기록·정리이며 새 웹 UI 제작이나 운영 UX 구현을 하지 않음. 원본 시안 HTML은 내용을 고치지 않고 이동. 실제 UI 구현 착수 시 저장소가 요구하는 디자인 SKILL.md와 pre-flight를 다시 확보해야 함. 이 문서 PR의 중단·승인 요청 조건으로 확대하지 않음.

## 근거와 해석

[독립 검토](2026-10-07-ux-ui-independent-review.md)는 이전 검토 환경의 관찰·소스 추정을 구분한다. 기준 main과 원본 시안을 함께 읽고 다음을 반영했다.

| 항목 | 판단 |
|---|---|
| 인원 변경·초기화·.sq 자동저장 | 원본 재현과 기준 main 소스가 일치하는 보호 우선순위. 이번 작업에서 새 실행 재현은 하지 않음 |
| 모바일 탭 | Claude Chromium 터치 에뮬레이션 관찰. 실제 Android 검증 대기 |
| PNG | 원본 검토에서 생성 성공. 고장으로 확정하지 않음 |
| 모바일 지침 | 이미 기본 접힘. 중복 신규 작업 제거 |
| A | 원본 나이트피치가 선택됨. 실제 캡처에서 모바일 전술 재생 버튼 우측 잘림 확인 |
| 이름/상태 동기화 | A 소스에 이름·패널 갱신 경로가 있음. 확정 고장으로 쓰지 않고 재현·수용 기준으로 기록 |
| 파일 목록 | A 안에서 찾기 쉬운 진입 경로를 제안. C 전체 채택을 뜻하지 않음 |

원본 캡처는 색상·배치 증거이며 실제 저장·광고·구매 구현 증거가 아니다. 과거 기획의 가격·구독·무료 계정/클라우드 우선 가설은 최신 사용자 방향과 충돌하므로 보관 영역으로 이동했다.

## 확정·가정·미정

확정은 [상품 기획서](product-plan.md)의 결정 표를 단일 기준으로 삼는다. 팀=프로젝트·전술=파일을 반영하되 슬롯 단위가 자동 확정되지는 않는다. 전술 파일 단위, 환불 시 초과 파일 자동 삭제 금지, Android 저장소·프레임워크·광고 위치는 제안/미정으로 표시했다.

기기 내 편집·저장과 광고 SDK 통신, 정적 공유 뷰어, 피드백 서버, 후속 팀 서버를 구분했다. 구매 권한 복원은 삭제된 파일 복구가 아니다.

## 문서 정리 원칙과 완료 기준

- 최신 진입점 docs/README.md → product-plan.md. 루트 README는 현재 웹 기능·실행/검증 참고와 최신 계획을 구분한다.
- A 원본과 6개 캡처를 docs/design-a로 모음. B/C·과거 비교안과 계획을 archive에 표시·보관.
- 과거 가격·광고 가설의 필요한 안전 원칙만 최신 기획에 통합. 원본 리뷰·테스트 증거와 Git 이력 보존.
- AGENTS/CLAUDE, tests/vendor, 라이선스 관련 자료, 운영 파일은 삭제하지 않음.
- 전체 문서·HTML의 내부 링크·이미지 참조를 이동 매핑에 맞춰 검사. 원본 캡처 blob 동일성, 비문서 경로 blob 동일성 확인.
- 전용 브랜치에 Conventional Commit으로 게시하고 Draft PR 생성. 검증 범위·차단·미정 목록을 보고.

전체 분류·이동·검증 결과는 [문서 정리 기록](documentation-audit.md)에 둔다.
