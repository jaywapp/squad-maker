## 1. 결정의 상태

| 표시 | 의미 |
|---|---|
| 확정 | 사용자가 선택한 제품 방향. 구현·출시 완료를 뜻하지 않는다 |
| 제안 | 구현 전에 검토할 설계·운영 원칙. 사용자 결정으로 바꾸지 않는다 |
| 미정 | 답변 또는 기술 검증이 필요하다. 수량·가격·기술을 임의로 채우지 않는다 |
| 현 구현 | 기준 main `e5877ddf198aaf54082d535a8c1894c346984973`에서 확인한 웹앱 동작 또는 소스. Android 구현과 구분한다 |

**확정**: Android 첫 출시. 1차는 로그인 없이 전술 편집, 기기 내 저장, 이미지·GIF 저장 및 공유, 광고를 포함한다. 무료 보관량은 동시에 보관하는 재사용 가능한 슬롯이며 삭제하면 다시 쓴다. 수정·자동저장은 슬롯을 차감하지 않는다. 추가 슬롯은 단건 결제로 영구 확장한다. 2차는 광고 제거와 지속적인 팀 공간에서 전술을 공유·관리하는 방향이다. 유료 상품이 반드시 정기 구독이라는 결정은 없다.

**미정**: 무료 슬롯 개수, 확장량, 가격, 슬롯의 정확한 단위, 결제 도입 시점, Android 프레임워크. 광고 SDK·위치·빈도, 출시 국가·대상 연령, 공유 수단의 우선순위, 2차 권한·요금 방식도 결정이 필요하다. 시안의 “3 / 3”은 데모 값이다.

**제안**: 전술 파일 1개를 보관 단위로 세는 안을 우선 검토한다. 기본·공격·수비는 파일 안의 상태로 두고 별도 슬롯으로 세지 않는 안이다. 사용자가 단위를 확정하기 전에는 과금 계약·저장 제한을 구현하지 않는다. Capacitor는 검토 후보이며 확정 스택이 아니다.

## 2. 사용자, 문제, 목표

주 사용자는 동호회·아마추어 축구의 코치, 감독 역할을 맡은 팀원이다. 경기 전 스마트폰에서 선수 배치와 약속된 움직임을 만들고, 기존 단톡방 등으로 전달하며, 다음 경기 때 다시 찾아 고친다. 받는 선수는 이미지·GIF 또는 기존 공유 뷰어로 전술을 이해한다. 1차에는 코치와 선수의 서비스 계정·팀 가입을 요구하지 않는다.

| 실제 문제 | 제품 목표 | 확인 방법 |
|---|---|---|
| 이름·배치·패턴을 바꾼 뒤 인원 변경으로 작업을 잃을 수 있음 | 파괴적 변경 전에 영향 설명·취소·되돌리기 제공 | 데이터 보호 시나리오 전후 상태 비교 |
| 경기 직전 폰에서 피치·편집 도구·재생 버튼 접근이 어려움 | A의 피치 중심 구조에서 모든 주요 행동이 도달 가능 | 실제 Android 과제 관찰 및 화면 측정 |
| 저장, 결과물 내보내기, 백업의 의미가 섞임 | 저장 상태와 행동 이름을 구분 | 초보 사용자의 이미지 공유·복원 과제 |
| 재사용할 전술을 찾기 어려움 | 팀=프로젝트, 전술=파일의 일관된 목록 | 목록에서 지난 전술 열기·수정·재사용 |
| 기기 데이터와 구매 권한의 복원을 혼동할 수 있음 | 백업 복원과 구매 복원을 별개로 안내 | 재설치·새 기기·잘못된 계정 시나리오 |

첫 출시는 “오늘의 전술 작성 → 이 기기에 안전하게 보관 → 그림으로 전달 → 다음에 다시 편집”을 완성한다. 일정·출석·회비·경기 통계, 고급 영상·PDF, AI 분석, 선수별 열람 추적, 조직 관리, 새로운 실시간 협업은 이번 필수 범위에 넣지 않는다. 과거 Pro/Club·가격·무료 계정 가설은 [이력](archive/README.md)에 남기고 최신 요구사항으로 사용하지 않는다.

| 경계 | 1차에서의 역할 |
|---|---|
| 앱 내부 로컬 저장 | 전술 원본과 팀 프로젝트 보관. 편집·저장·내보내기는 네트워크에 의존하지 않도록 제안 |
| 광고 SDK 통신 | 광고 요청·측정·동의 처리 등 외부 사업자 통신. 전술 편집 저장소와 별개 |

| 피드백 서버 | 현 `api/feedback.js`가 사용자가 보낸 제보를 중계. 전술 자동 업로드 저장소가 아님 |

| 2차 팀 서버 | 지속적인 팀 공간, 접근 권한과 공유 관리를 맡을 후속 범위 |

## 4. 정보 구조와 용어

**확정 개념**: 팀은 프로젝트, 전술은 파일이다. **제안 구조**는 아래와 같다.

```text
이 기기의 팀 목록
└─ 팀 프로젝트 (팀 이름)
   └─ 전술 파일 (파일 이름, 수정 시각, 저장 상태)
      ├─ 공통 명단·매치 정보
      ├─ 기본 상태: 포메이션·배치·팀 지침·선수 지침
      ├─ 공격 상태: 포메이션·배치·팀 지침·선수 지침
      ├─ 수비 상태: 포메이션·배치·팀 지침·선수 지침
      └─ 전술 패턴 목록 → 패턴 → 단계별 선수·공 이동
```

현 구현은 공통 `roster`, `squads[basic|attack|defense]`, 별도의 `patterns`를 하나의 `v:1` 스냅샷에 저장한다. 여러 팀·전술 파일 저장소와 구매 슬롯은 현 구현에 없다. 시안의 “전술 파일” 목록은 실제 저장소가 연결된 것이 아니다. 후속 설계에서 전술 파일과 움직임 패턴을 다른 개념으로 정의해 목록에서 열기와 패턴 전환이 섞이지 않게 한다. 현 v:1 직렬화는 v/team/mode/squad/roster/squads/pat를 사용한다. 매치 정보 입력은 현 v:1에 저장되지 않으므로 위 파일 구조의 매치 정보 보관은 별도 제안이다. 기존 패턴은 임의로 기본·공격·수비에 재배속하지 않는다. 시작 배치 기준은 현 누적 단계 계약을 먼저 검증한다.

**제안 라벨**:

| 대상 | 화면 라벨 / 안내 |
|---|---|
| 프로젝트 진입 | “팀 목록”, 현재 팀 이름 |
| 파일 진입 | “전술 목록”, 현재 전술 이름, “새 전술” |
| 편집 작업 | “배치”, “움직임 패턴” |
| 상태 선택 | “기본”, “공격”, “수비”; 선택 상태를 편집 패널에도 동일하게 표시 |
| 피치 복원 | “현재 배치 초기화”; 어떤 상태에 적용되는지 확인문에 명시 |
| 앱 보관 | “이 기기에 저장됨”, “저장 중”, “저장 실패” |
| 결과물 | “이미지 저장”, “GIF 저장”, “공유” |
| 편집 원본 파일 | “백업 파일 받기(.sq)”, “백업에서 복원” |
| 텍스트 출력 | “전술 텍스트 받기” |
| 상점·복원 | “슬롯 확장”, “구매 복원” |

“파일 저장” 하나로 자동저장·텍스트 다운로드·백업을 함께 부르지 않는다. 숫자만 있는 슬롯 바 대신 “보관 중 {사용량} / {한도}”와 정책 설명을 제공한다. 단위가 확정된 뒤 명칭과 카운터를 맞춘다.

## 5. A 시각 원칙

**확정**: A의 피치 중심 코치형 방향을 선택했다. B의 전체 안내형 단계 구조나 C의 전체 파일 탐색·타임라인을 선택한 것은 아니다. 파일 접근성이라는 필요만 A 안에서 해결한다.

**A 원본 확인**: 다크 그린 배경·녹색 피치·라임 주 행동, 선수 이름의 짙은 배경, 선택 선수 편집 패널, 데스크톱의 피치 중심 배치, 모바일 선택 도구와 전술 선택 영역. 실제 캡처·원본 데모는 [A 자료](design-a/README.md)에 있다. 저장·구매·광고는 데모 표현이다.

**제안 개선**:

- 라임은 주요 행동·선택 강조에 집중한다. 파괴적 행동은 분리하고 텍스트로 의미를 전달한다.
- 선수 이름은 피치 선과 겹쳐도 읽히는 배경을 유지하고, 긴 이름의 표시는 말줄임·선택 시 전체 이름 노출을 함께 검토한다. 한글·큰 글자에서 잘림을 확인한다.
- 선수 라벨 목표는 화면상의 유효 크기 12~14sp부터 검증하고 보조 정보는 14sp, 본문·입력은 16sp를 우선 검토한다. 실제 크기는 사용자 검증 뒤 확정한다.
- 주요 터치 영역 48dp 이상, 본문 대비 4.5:1 이상을 검증 목표로 둔다. 글자 확대·TalkBack·키보드 포커스·모션 줄이기를 포함한다.
- 모바일은 피치 크기만 늘려 도구를 화면 밖으로 밀지 않는다. 재생·단계 이동은 폭이 부족하면 두 줄로 재배치하고 재생 버튼을 고정한다.
- “전술 목록” 버튼을 상단의 현재 전술 이름 근처에 항상 노출하는 안을 제안한다. 목록은 시트로 열고 닫으면 같은 피치·선택·스크롤로 돌아온다.
- 기본·공격·수비의 선택 상태, 선수 이름, 패턴 이름을 피치·편집 패널·파일 헤더·내보내기 미리보기에서 함께 갱신한다. 현 시안의 이름 동기화 고장이 확인된 것은 아니며 수용 기준으로 추가한다.
- 모바일 개별 선수 지침은 현 구현에서 이미 기본 접힘이다. 다시 “기본 접힘 구현” 작업으로 세지 않고 회귀 확인한다.

## 6. 화면별 구성과 예외

아래는 후속 구현을 위한 **제안**이다. A의 전체 톤·피치 우선순위를 유지한다.

| 화면 | 주요 구성·행동 | 빈 상태·오류·취소·되돌리기 |
|---|---|---|
| 팀 목록 | 팀 이름, 전술 수, 팀 열기·이름 변경·삭제 | 처음에는 팀 생성 안내. 저장 실패면 입력 유지·재시도. 팀 삭제는 포함된 전술 영향을 보여주고 백업 제안·취소·되돌리기. 복구 보관 기간은 미정 |
| 전술 목록 | 현재 팀, 파일 이름·수정 시각, 보관 카운터, 열기·새 전술·삭제·백업 복원 | 빈 목록은 “새 전술 만들기”. 한도 도달은 기존 편집 허용·삭제 재사용·확장 안내. 열기 실패는 원본 보존. 삭제 취소는 변동 없음; 되돌리기와 슬롯 반환의 원자적 처리 필요 |
| 배치 편집 | 팀/파일 헤더·저장 상태·전술 목록, 기본/공격/수비, 인원·포메이션, 피치, 선택 도구, 내보내기·공유 | 선수 없음은 추가 안내. 상태 전환은 변경 보존. 인원 변경은 손실 대상을 설명·취소·되돌리기. 초기화는 현재 상태 범위만 표시. 저장 실패는 지속 경고와 백업 경로 |
| 선수 편집 | 이름·색상·지침·현재 상태 이름, 피치 선택 연결 | 빈 이름은 기본 표시 규칙. 입력 취소는 이전 값. 삭제는 영향 설명·취소·되돌리기. 소프트 키보드가 입력·완료를 가리지 않음 |
| 움직임 패턴 | 패턴 선택·이름, 시작 배치, 단계 목록·이동·추가·삭제, 피치, 재생/정지 | 패턴 없음은 만들기 안내. 경로 없는 단계의 재생 의미 설명. 단계/경로 삭제는 되돌리기. 재생 중 편집 정책 명시·정지로 복귀. 버튼 잘림 없음 |
| 내보내기·공유 시트 | 현재 파일/상태/패턴의 대상 표시, 이미지/GIF 미리보기, 저장·OS 공유, 링크·텍스트, 백업 구분 | 준비 중·성공·실패를 표시. GIF 취소는 원본 유지·오버레이 닫기. 공유 시트 취소는 실패로 오인하지 않음. 긴 링크는 복사 실패 안내·이미지 대안 |
| 백업 복원 | 파일 선택, 형식·버전·대상 요약, 새 파일로 가져오기 또는 교체 확인 | 파일 선택 취소는 변동 없음. 손상·지원하지 않는 새 버전·용량 초과는 원본 유지. 한도 도달은 무단 덮어쓰기 없이 대안 안내. 성공 후 기기 저장·재열기 검증 |
| 슬롯 확장/구매 복원 | 단건 영구 확장임을 설명, 실제 스토어 가격·증가량, 구매 상태·복원 | 취소·보류·네트워크 실패·이미 보유·다른 스토어 계정 안내. 확인된 구매만 1회 반영. 복원 성공과 로컬 파일 없음은 별도 메시지 |
| 지원·설정 | 도움말, 백업 안내, 개인정보·라이선스·버전, 의견 보내기, 구매 복원 | 제보 서버 장애는 초안 유지·재시도·복사 안내. 진단 정보의 수집 범위를 전송 전에 표시 |
| 공유 뷰어 | 공유된 스냅샷의 상태·패턴 재생·지침, 명시적 가져오기 | 잘못된 링크는 이유·재요청 안내. 열람만으로 수신자의 로컬 파일을 덮어쓰지 않음. 가져오기 취소·한도·중복 처리 확인 |

## 7. 주요 흐름

1. **첫 전술**: 앱 시작 → 로컬 팀 프로젝트 생성 → 새 전술 이름 → 기본 배치 → 이름·지침 편집 → 기기 저장 상태 확인 → 이미지/GIF 시트 → 저장 또는 OS 공유. 로그인·구매가 편집을 막지 않는다.
2. **재사용**: 팀 → 전술 목록 → 기존 파일 → 공격·수비 상태 수정 → 자동저장. 수정·재생·내보내기로 보관 카운터가 증가하지 않는다.
3. **한도 도달**: 새 파일 만들기/복원 시 정책 확인 → 현재 파일 편집 계속, 목록에서 삭제 후 재사용 또는 구매 도입 후 확장. 삭제 확인 취소 시 파일·카운터 그대로.
4. **위험한 변경**: 이름만 바꾼 상태에서도 인원 변경 영향 요약 → 취소하면 그대로 → 진행하면 변경 전 상태를 되돌릴 수 있음 → 되돌리기 후 저장·재시작에서 복구 상태 유지.
5. **기기 이동**: 이전 기기에서 백업 받기 → 새 기기에서 복원 → 파일·이름·세 상태·패턴 확인 → 구매 복원은 별도 실행. OS 자동 백업에만 의존하지 않는다.
6. **공유 받은 선수**: 이미지/GIF 열람 또는 기존 정적 링크 뷰어 → 필요하면 앱으로 명시적 가져오기. 공유 콘텐츠에 포함된 이름·지침 공개 범위를 생성자가 확인한다.

## 8. 저장, 백업, 복원, 공유와 버전

### 8.1 현 구현과 목표의 경계

현 웹은 LocalStorage `squad-maker-v1` 하나에 마지막 작업을 보관한다. `buildStateSnap()`/`restoreState()`, `v:1`, `.sq` JSON, URL `#s=`를 사용한다. 구형 단일 화살표 패턴의 1단계 변환과 외부 입력 sanitize가 있다. Android의 저장소·다중 파일·앱 재설치 복구는 아직 구현되지 않았다.

**제안**: 팀/파일 메타데이터와 전술 내용 저장을 분리하되, 상태와 저장 카운터를 하나의 성공 단위로 처리한다. “저장됨”은 쓰기 완료 후만 표시한다. 실패한 변경은 메모리에 유지하고 재시도·백업을 제공한다. 앱 강제 종료·백그라운드·저장 공간 부족에서 마지막 성공 저장본을 보존한다. 지원할 Android 저장소는 프레임워크 결정과 실험 뒤 확정한다.

### 8.2 문서 버전 계약 제안

| 버전 | 역할 |
|---|---|
| 이 기획서의 1.0 | 사람이 읽는 요구사항 개정 번호 |
| `schemaVersion` (제안) | 새 팀/전술 보관 문서의 읽기·검증·이전 규칙 |
| `v:1` | 기존 전술 스냅샷 형식. 임의로 새 버전 숫자에 맞춰 바꾸지 않는다 |
| `revision` (제안) | 같은 파일의 저장 변경 구분. 2차 충돌 처리용 확장 가능 |
| 백업/공유 형식 버전 (제안) | 컨테이너·포함 범위의 버전. 내부 스냅샷 버전과 별개 |

후속 설계에서 안정적인 팀·파일 ID, 생성·수정 시각, 파일 제목, 포함 상태, 패턴, 형식 버전을 정의한다. 구매 토큰·권한은 사용자가 전달하는 전술 백업/공유 파일에 넣지 않는다. 알 수 없는 새 버전은 무리한 복원 대신 지원 불가 안내를 제공한다.

### 8.3 이전과 복원

- 기존 LocalStorage/`.sq`/`#s=`의 `v:1` 읽기를 회귀 계약으로 보존한다. 원본을 복사한 뒤 검증·변환·시험 저장·재읽기를 마치고 활성화한다. 원본 삭제는 자동으로 하지 않는다.
- 웹 브라우저의 로컬 데이터를 Android 앱이 자동으로 읽을 수 있다고 가정하지 않는다. 1차 이전 경로는 사용자가 받은 `.sq` 파일 가져오기를 우선 검토한다.
- 가져오기 전에 내용·버전·대상·슬롯 영향을 요약한다. 파일 새로 만들기와 현재 파일 교체를 구분한다. 실패·취소는 원래 파일과 카운터를 보존한다.
- 성공한 복원은 즉시 영속 저장하고, 앱 재시작 후 같은 데이터가 남는지 확인한다. 교체 직전 상태를 되돌릴 수 있는 안을 제안한다.
- 백업은 편집 원본이다. PNG/GIF는 설명용 결과물로 편집 원본 복원을 보장하지 않는다. 전체 팀/전술 백업 범위·확장자는 후속 결정이며 기존 `.sq` 읽기는 유지한다.
- 자동저장은 백업과 다르다. 앱 삭제·저장 데이터 초기화·기기 분실 시 복구하려면 별도 백업이 필요함을 안내한다. 휴지통·장기 복구 이력·클라우드 백업은 확정 기능이 아니다.

### 8.4 공유

**확정**: 1차 이미지/GIF 저장·공유. **현 구현 유지 대상**: 기존 스냅샷 링크와 비회원 뷰어. **제안**: Android OS 공유 시트에 사용자가 선택한 PNG/GIF를 전달하고 취소·실패를 구분한다. 공유 생성은 스냅샷이며 원본 수정이 이미 보낸 이미지/GIF/URL에 자동 반영되지 않는다.

기존 `#s=` 링크는 콘텐츠가 인코딩된 링크이며 비공개 권한·만료·취소가 있는 관리형 팀 공유가 아니다. 링크 길이·메신저 호환성과 포함된 선수 이름·지침을 확인한다. 정적 뷰어를 팀 공간이라고 안내하지 않는다. 2차의 지속적인 공유는 별도 문서·접근 권한 계약으로 설계한다.

## 9. 슬롯과 단건 구매

### 확정 원칙

- 무료 슬롯은 동시에 보관하는 재사용 가능한 공간이다. 생성 횟수·편집 횟수·저장 횟수 쿠폰이 아니다.
- 삭제하면 다시 사용한다. 수정·자동저장·미리보기는 차감하지 않는다.
- 추가 슬롯은 단건 결제로 영구 확장한다. 기간 만료·정기 갱신을 임의로 붙이지 않는다.
- 구매 권한 복원은 이용 가능한 보관 한도를 회복하는 일이다. 삭제된 로컬 전술 데이터를 되살리는 백업 복원과 다르다.

### 제안 계약과 미정 경계

정확한 단위가 결정되면 `사용량 = 현재 보관 중인 해당 단위 수`, `한도 = 무료량 + 확인된 영구 확장량`으로 계산한다. 슬롯 정책 버전을 기록하고 기존 웹 사용자 데이터에 대한 전환 정책도 사용자에게 결정받는다. 기존 무료 기능·파일을 갑자기 삭제하거나 유료 잠금하지 않는 안을 제안한다.

| 상황 | 제안 처리 |
|---|---|
| 신규 생성·복제·새 파일 가져오기 | 영속 저장 성공 시 한 번 증가. 실패/취소면 증가 없음. 파일 단위 확정 전 적용 보류 |
| 같은 파일 수정·자동저장·교체 복원 | 기존 단위 수 유지 |
| 삭제·삭제 되돌리기 | 삭제 성공 즉시 재사용. 되돌리기 중 새 파일이 슬롯을 사용했으면 자동 삭제 대신 충돌 안내·백업/선택 제공 |
| 구매 취소/실패/보류 | 확인 전 확장 없음. 원래 전술 유지. 보류→완료는 한 번만 반영 |
| 동일 구매 재전달·복원 반복 | 구매 식별 기준으로 멱등 처리. 권한을 중복 증액하지 않음 |
| 재설치·기기 교체 | 스토어 계정의 구매 권한을 확인해 복원. 로컬 전술은 사용자 백업 등 별도 경로 |
| 오프라인·조회 오류 | 확정된 캐시 권한과 검증 미완료 표시 정책을 기술 검토. 조회 실패를 환불로 간주하지 않음 |
| 환불·권한 취소 후 초과 보관 | **제안: 초과 전술을 자동 삭제하지 않는다.** 열기·편집·백업을 보호하고 신규 추가 제한/정리 안내를 검토. 최종 환불·초과 정책은 사용자 결정 |

단건 영구 확장을 Play 상품으로 어떻게 표현할지, 반복 확장 상품의 중복 구매와 복원 기록을 어떻게 보장할지는 미정이다. 단순한 소모성 구매 처리만으로 영구 복원이 해결된다고 가정하지 않는다. 최소 권한 검증·구매 확인·환불 반영이 자체 팀 서버 없는 목표와 양립하는지 도입 전에 검증한다. Google Play 판매 시 최신 지역별 결제 정책·예외를 확인하고 해당 경로를 결정한다. [Play 결제 정책](https://support.google.com/googleplay/android-developer/answer/9858738?hl=en), [결제 연동과 구매 처리](https://developer.android.com/google/play/billing/integrate), [단건 구매 생명주기](https://developer.android.com/google/play/billing/lifecycle/one-time)

## 10. 광고, 개인정보, 라이선스와 지원

### 광고

**확정**: 1차 광고 포함, 2차 광고 제거 방향. SDK·형식·노출 빈도·제거 상품은 미정이다. **제안**: 피치·선택 도구·삭제/되돌리기·복사/공유 행동에서 떨어진 목록 또는 완료 영역을 후보로 검토한다. 광고 자리 크기를 예약하고 무광고/광고 실패에서도 편집 화면을 밀지 않는다. 광고 요청 실패·오프라인·동의 거절이 저장·내보내기를 막지 않게 한다. 결과물을 얻기 위해 강제 광고 시청을 요구하는 기능은 확정하지 않는다.

옛 광고 문서의 공유 모달 내 광고·앵커·인터스티셜·고정 빈도는 과거 웹 제안이다. 그대로 Android 구현 지시로 사용하지 않는다. 테스트 광고로 오클릭·닫기·배경 복귀·TalkBack을 점검하고 SDK 및 지역·대상 연령에 맞는 동의/광고 정책을 확인한다. [Google Play 광고 정책](https://support.google.com/googleplay/android-developer/answer/9857753?hl=en)

### 개인정보

로그인 없는 로컬 중심이라도 광고 SDK·피드백·공유 대상 앱의 통신을 별도로 설명한다. 출시 전 데이터 흐름 표에 실제 수집 항목, 목적, 사업자·처리 국가, 보유/삭제, 필수/선택, 동의·권리 경로를 적고 네트워크 관찰과 대조한다. 전술 이름·선수 이름·지침·스냅샷을 광고·분석 속성이나 자동 진단에 넣지 않는 안을 제안한다. 피드백 첨부는 사용자가 확인한 범위만 보낸다.

**현 구현**의 분석 ADR·이벤트 사전은 기존 웹 운영 참고 자료다. 이 PR은 활성화 상태·키·전송 설정을 변경하지 않는다. Android 수집 여부는 새 검증이 필요하다. 개인정보처리방침과 스토어 Data safety는 실제 SDK 동작까지 반영한다. [Google Play Data safety 안내](https://support.google.com/googleplay/android-developer/answer/10787469?hl=en)

### 라이선스와 지원

기준 트리에 저장소 루트 LICENSE는 없다. 배포 권리를 임의로 새 라이선스로 확정하지 않는다. html2canvas·gif.js/worker·테스트 vendor·글꼴·아이콘·스토어 자산의 원본 및 라이선스/고지 의무를 확인하고 Android에 묶을 자산의 고지 목록을 만든다. 외부 CDN 의존을 제거하는 안은 라이선스 확인 후 검토한다.

지원 화면은 앱/데이터 형식 버전, 기기 정보의 최소 진단, 도움말, 구매 복원, 백업 경고, 피드백 경로를 제공하는 안이다. 결제 권한 문제와 전술 유실 문의를 나눠 안내한다. 문의 담당자·연락처·응답 기준은 출시 전에 결정한다. 기존 제보 서버의 출처 검증·제한과 테스트 증거는 보존한다.

## 11. 우선 재현·보호 계획

원본 검토의 실행 환경과 기준 커밋이 서로 다르므로 후속 구현 착수 시 최신 소스에서 재현 기록을 먼저 만든다. 이 문서 정리 작업에서 앱을 고쳤거나 실제 Android로 검증했다고 주장하지 않는다.

## 13. 작업 의존성

데이터 보호 → 로컬 저장 계약과 이전 → A 편집·목록·내보내기 → Android 패키징·실기기 검증 → 광고·스토어 게이트 순서가 기본이다. 프레임워크 비교 실험은 데이터 보호와 독립적으로 진행할 수 있다. 슬롯 구매는 단위·수량·상품/권한 복원 결정 뒤 별도 가지로 착수한다. 2차 팀 공간은 1차 저장 문서 호환성과 별도 계정·권한·요금 설계에 의존한다.

세부 계약은 [저장·화면 설계](squad-product-20261007-design.md), 실행 순서와 차단 항목은 [작업 계획](squad-product-20261007-tasks.md)에 있다.
