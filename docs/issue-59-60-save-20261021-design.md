# #59·#60 저장 광고 — 검토 설계

2026-10-22 직접 사용자 확인으로 첫 저장 면제 범위를 확정했다. 아래는 구현 기준이며 실행 결과는 별도 보고에 기록한다.

## 확정된 기능 방향

- 명시적 PNG/GIF/SQ 저장은 실제 파일 쓰기 성공을 먼저 확인한다. blob 생성, 파일 선택, Share.share 반환, 웹 다운로드 요청은 저장 광고 근거가 아니다.
- 저장 완료 상태/안내를 확정한 뒤 자연스러운 전환점에서 이미 준비된 광고만 평가한다. 로드 대기·임의 지연 타이머·다음 resume 예약은 없다.
- 광고 실패/취소/조건 불일치가 성공한 파일을 재저장하거나 저장 결과를 실패로 바꾸지 않는다.
- 공유와 자동저장은 광고·면제·cooldown에서 제외한다. 10분은 전역이며 실제 show에서만 한 번 갱신한다. 기존 연령/UMP/캐시/시계 역행 보호를 약화하지 않는다.

## 인터페이스와 구현 기준

1. Documents 플러그인은 성공한 쓰기의 일회성 완료 근거와 현재 작업/생명주기 정보를 native에 보관한다. JS가 임의로 success를 만들어 첫 면제나 표시를 소모하지 못하도록 해야 한다. 공개 응답에는 파일 경로/바이트/개인정보를 추가하지 않는다.
2. JS는 명시적인 native success만 `file-saved`로 매핑한다. 기존 결과 의미와 오류/취소/웹 다운로드/공유 결과는 유지한다.
3. 편집기에서 저장 성공을 먼저 알리고 그 완료 기회에 묶인 준비된 광고 평가를 요청한다. UI 완료와 광고 사이에 새로운 편집/공유/배경 이동이 있으면 기회를 폐기한다. 실제 사용자가 저장 완료를 인식할 자연스러운 경계인지 UI 검토가 필요하다.
4. native는 실제 파일 쓰기 성공 때 첫 저장 기록을 원자적으로 영속화한다. 첫 성공 저장에는 광고 근거를 발급하지 않는다. 이후 성공에만 MIME에 맞는 일회성 광고 근거를 발급한다. 기록 쓰기 실패·중복/오래된 근거·불명확한 상태는 광고 skip이고 파일 성공은 유지한다.
5. `exportFile`의 내부 결과에 `adReceipt` 문자열/null을 포함하고 공개 UI 계약 결과에는 근거를 노출하지 않는다. `showExportAd(placement, receipt)`는 `save-png`, `save-gif`, `save-sq`와 일치하는 근거가 있을 때만 native로 전달한다. 기존 `gif/sq/share-text` 직접 호출은 거부한다. 첫 성공 여부는 JS 광고 호출 유무와 무관하게 native 실제 저장 성공에서 기록한다.
6. 완료 기회는 native 공유/pause/resume/destroy로 무효화하며, 발급 이후 로드된 광고로 나중에 표시하지 않도록 발급 순간의 광고 준비/동의/활성 조건을 함께 기록한다. 명시 저장 완료 안내를 먼저 갱신한 뒤 즉시 같은 작업의 광고만 평가한다. 로드나 resume을 기다리는 타이머는 두지 않는다.
7. SDK 표시 후 닫힘 콜백 미수신 등으로 편집기가 영구 busy가 되지 않도록 광고 응답 대기만 제한한다. 이 제한은 지연 광고를 예약하는 타이머가 아니다. 제한 만료 후 근거를 무효화하고 파일 성공을 반환하며 이미 SDK에 전달한 광고를 강제 종료한다고 주장하지 않는다. native는 실제 callback 전 activeShow 예약을 함부로 해제해 중복 광고를 허용하지 않는다.
8. 완료 근거는 파일 close 성공 시점부터 1초 미만으로 제한한다. 파일 close 뒤 면제 기록 commit이 지연되거나 main thread가 지연되면 skip한다. 근거 소비와 실제 SDK 전달 사이에도 불변 snapshot의 시각·epoch·광고 identity·캐시 유효성을 다시 확인한다. 표시용 지연 타이머는 없다.
9. 첫 성공 기록은 앱 전용 SharedPreferences의 별도 키로 동기 commit한다. 프로세스 전체에서 직렬화하며 commit 실패/예외 뒤에는 메모리 값이 true여도 해당 프로세스의 광고를 계속 skip한다. 이 키는 .sq 및 전술 저장 형식에 포함하지 않는다.
10. Documents callback은 staged token별로 한 번만 처리한다. 재생성 후 복원 callback은 파일 쓰기를 완료할 수 있지만 이전 광고 기회를 복원하지 않는다. 실제 쓰기 성공은 면제 기록을 처리하며 광고 실패가 파일 결과에 영향을 주지 않는다.

## 대안·위험

- 단순히 JS의 `completion` 문자열만 받아 광고를 띄우면 중복 호출/재시작/위조된 성공을 native가 구별하기 어렵다. native에서 실제 쓰기와 연결하는 설계가 더 명확하다.
- 모든 파일 저장을 광고 상태와 함께 하나의 결과로 합치면 광고 실패가 저장 실패처럼 보일 수 있다. 파일 결과는 독립적으로 유지해야 한다.
- Documents provider의 스트림 close 성공은 앱이 확인할 수 있는 쓰기 완료다. 외부 클라우드 동기화까지 성공했다고 안내하지 않는다.
- pause/resume 때마다 새 광고 기회를 만들지 않는다. picker 복귀 자체도 저장 성공이 아니며 쓰기 완료·활성 상태를 함께 확인해야 한다.
- 승인되지 않은 영속 정책 대신 세션 단위 첫 저장 면제를 구현하는 우회는 하지 않는다.

## 검증 전략

| 층 | 필수 케이스 |
|---|---|
| 파일 성공 판정 | success만 인정, cancelled/error/누락/unknown은 광고0, write/flush/close 실패 |
| 순서 | 실제 file-saved → 저장 완료 상태 → 선택적 광고, 광고 실패 뒤 저장 success 불변 |
| 면제 (정책 확정 후) | 첫 성공, 실패→성공, 두 번째 저장, 기존 설치/새 설치, 재시작, 영속화 실패, 중복/동시 결과 |
| 빈도 | PNG→GIF→SQ 공통, 9:59/10:00, clock-back, show callback 중복, no-fill/show-failed는 비갱신 |
| 생명주기 | picker 취소, 쓰기 중 배경 이동, 완료 직후 공유/외부 이동, 회전/재생성, stale callback 폐기 |
| 회귀 | 공유 광고0, 자동저장0, .sq 복원/저장/재시작 보존, 기존 UMP/연령 보호 |

로컬 mock/Java 정책/E2E와 실제 Android 시스템 picker·광고 SDK·Activity 검증은 별도로 보고한다. 실제 실행 결과는 [검증 보고](issue-59-60-save-20261021-report.md), 남은 기기 검증은 [체크리스트](issue-59-60-save-20261021-device-checklist.md)에 기록한다.
